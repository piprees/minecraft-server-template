# Skill brief: `web-surface-branding`

> **This is a brief, not the skill.** Build `SKILL.md` from it; verify every path against the repo before writing.

## Why this skill

Four public web pages share one design system and **have no shared stylesheet** — each surface carries its own copy. The nav bar is not authored per page at all: it is `sub_filter`-injected by nginx in **four near-identical copies** (one per `server` block) plus a fifth inside the map-sleeping fallback page. Changing the nav means changing all five, and nothing checks that you did.

This is the definition of a skill-shaped problem: a simple-sounding task ("change the nav link colour") that touches five files an agent would never find, in three different languages, across three deploy tiers. `README.md § Web surfaces` documents the map in a table; `DESIGN.md` holds the tokens; neither is reachable from the task.

There is also a nice, non-obvious mechanism worth teaching: the footer version string is computed three different ways depending on which surface renders it, because two of them run in containers with no git checkout.

## Scope

**In:** changing how any public page looks or reads. The four surfaces, where each one's markup and styles live, the nav injection, OG/meta tags, the design tokens, fonts, the version string, and which deploy tier each change triggers.

**Out:** the seed viewer (`scripts/seed/viewer_template.html`) — internal tooling, not a public surface; mention it exists and is out of scope. The Cloudflare maintenance Worker → brief 12.

### SKILL.md must contain

1. **The surface table, first**, exactly as `README.md` has it but with a "how to verify it changed" column added:
   | Surface | Markup + styles | Regenerated by | Deploy tier |
   | --- | --- | --- | --- |
   | pack.DOMAIN | `modpack/template/index.html` | `build-modpack.sh` → `modpack/dist/index.html` | Pull (CI rebuilds pack) |
   | mods.DOMAIN | heredocs in `scripts/check-updates.sh` (`--html`) | mod-checker container, boot + 06:00 UTC | Infra |
   | status.DOMAIN | Uptime Kuma + `customCSS`/`footerText` in `kuma-config.json` | kuma-init, every deploy | Infra |
   | map.DOMAIN | BlueMap webapp (upstream); the "map sleeping" fallback is inline HTML in `nav-proxy.conf` | — | Infra |
   | 404 | heredoc in `build-modpack.sh` | `build-modpack.sh` | Pull |
2. **The nav-injection warning as its own heading, not a footnote.** Five copies. List them explicitly (four `server` blocks in `nav-proxy.conf.template` + the map-sleeping page), and mention `nav-proxy-local.conf` as a sixth for local dev. A change that updates four of five ships a broken nav on one domain.
3. **`DESIGN.md` is the source of truth for tokens**, kept in step **by hand**. Every surface copy must be updated together. State that there is no build step enforcing this — it is the skill's job to.
4. **The named rules**, quoted, because they are what makes a change good rather than merely valid: the Hearth Rule (copper on ≤10% of surface), the Mineral Tint Rule (neutrals carry chroma toward hue 240, never pure grey), the One Family Rule, the Flat Stone Rule (no structural shadows).
5. **The do's and don'ts**, verbatim from `DESIGN.md § 6`. They are unusually specific anti-references (no Tailwind Slate, no blue accents, no uppercase tracked eyebrows, no glassmorphism, no scroll-reveal, no bounce easing) and an agent will violate every one by default.
6. **The footer version string**, because it looks broken when it isn't: `PACK_NAME` is computed by `build-modpack.sh` from the git sha; the mods and status pages run in containers with no git checkout and read the *served* pack build instead (`modpack/dist/packwiz/pack.toml`, and `http://pack-web/packwiz/pack.toml` respectively). **`vunknown` on the status footer means pack-web was unreachable and no git checkout existed** — that is the diagnostic, not a bug in the footer.
7. **Fonts**, with the constraint: the placeholder uses system fonts; a custom display font goes in `modpack/template/fonts/` (copied to `dist/fonts/` by the build), needs the CSS updated in each surface, and needs a CORS header on `/fonts/` in `pack-web.conf` if Kuma's `customCSS` loads it cross-origin. CSP is `font-src 'self' data:` — no external fonts.

### Traps to capture

1. **Five nav copies.** Change all of them. Six with the local config.
2. **No shared stylesheet.** Editing one surface's CSS changes exactly one surface.
3. **Kuma's HTML cannot be edited** — only `customCSS` in `kuma-config.json`. And that file is authoritative: UI edits are reverted by kuma-init on the next deploy.
4. **`/mods/` in `pack-web.conf` must return a clean 404**, not the site-wide 301-to-homepage, or launchers download HTML instead of falling back to the Modrinth CDN.
5. **`.toml` files must never become edge-cached** — the packwiz index is the auto-update signal. `.toml` isn't in Cloudflare's default cache list; keep it that way.
6. **`modpack/dist/` is build output.** Never hand-edit `dist/index.html`, `dist/mods/` or `dist/packwiz/`.
7. **Deploy tiers differ per surface.** A pack-page change is pull tier (CI rebuilds the pack); a nav or Kuma change is infra tier and force-recreates a container. Predicting the wrong tier means waiting for a change that was never going to deploy.
8. **OG/meta tags are injected per-domain** by `sub_filter '<title>'` in `nav-proxy.conf` — they are not in the page source.

### Validation section

```bash
docker exec nav-proxy grep -c '<nav' /etc/nginx/conf.d/default.conf   # expect the copy count you edited
curl -sI https://mods.example.com | head -5
curl -s https://pack.example.com | grep -o '·[^<]*</'                 # footer version string
./ops restart nav-proxy && ./ops restart pack-web                     # force-recreate to load config
```

Reinforce the rule from `local-stack-testing`: verify the **rendered** config inside the container, never the file you edited.

## Done when

- An agent asked to change the nav updates all five (six) copies and says which it changed.
- An agent asked to restyle the status page reaches for `kuma-config.json` `customCSS`, not Kuma's HTML.
- The skill reproduces `DESIGN.md`'s do's and don'ts rather than paraphrasing them — the specificity is the value.
