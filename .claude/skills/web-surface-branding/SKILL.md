# Web surface branding

You are changing the look, copy, or metadata of one of this platform's public web pages. **Out of scope:** `scripts/seed/viewer_template.html` (the seed-rolling viewer — internal tooling, not a public surface) and the Cloudflare maintenance Worker (`config/cloudflare/maintenance-worker.js` — covered by the server-provisioning skill, not this one).

## Nav injection — four copies, not five or six

The nav bar is **not authored per page** — it's `sub_filter`-injected by nginx. `config/nginx/nav-proxy.conf.template` has exactly **four** `server` blocks (`map`, `status`, `pack`, `mods`), each with its own `sub_filter '</body>' '<nav class="site-nav">...'` injection and its own hard-coded `aria-current="page"` link. Verify the count yourself, every time, before and after a change:

```bash
grep -c '<nav' config/nginx/nav-proxy.conf.template   # must return 4
```

Change all four or you ship a broken/stale nav on whichever domain you missed.

**There is no fifth copy and no sixth.** Two things older material claims exist and don't:

1. A "map sleeping" fallback page — doesn't exist (see the correction above; map.DOMAIN has no upstream to sleep).
2. A `config/nginx/nav-proxy-local.conf` feeding a separate local-dev nav variant — this path is `.gitignore`d, untracked, and referenced by nothing (`docker-compose.yml` renders the same `nav-proxy.conf.template` for both the `local` and `cloud` Compose profiles, just with a different `DOMAIN` value). If it exists on your disk it's most likely a stray empty directory left by Docker auto-creating a bind-mount target that was never a real file — not a config surface to edit.

OG/meta tags are injected the same way, in the same four blocks: `sub_filter '<title>' '<meta property="og:...">...'`. They exist only in the rendered nginx output, never in any surface's actual page source.

## DESIGN.md is the source of truth — kept in step by hand

`DESIGN.md` (repo root) defines every colour, font, and spacing token. **There is no build step that propagates it.** Each surface below carries its own hard-coded copy and must be updated in the same commit as any `DESIGN.md` change:

- `modpack/template/index.html` — CSS custom properties in a `:root` block (comment explicitly says "single source of truth: DESIGN.md")
- `scripts/check-updates.sh` — hard-coded hex inline, no custom properties
- `config/uptime-kuma/kuma-config.json` `statusPage.customCSS` — hard-coded hex inline
- `config/nginx/nav-proxy.conf.template` — the injected `.site-nav` CSS, duplicated per server block

Full palette and duplication map: `references/design-tokens.md`.

### Named rules (quote these when reviewing a change)

- **The Hearth Rule.** Copper appears on primary actions and step markers only. Its rarity is the warmth. If copper is everywhere, the hearth has gone out.
- **The Mineral Tint Rule.** Neutrals carry 0.015-0.02 chroma toward hue 240 (slate-blue). Never pure grey, never warm-tinted.
- **The One Family Rule.** If you add a display font, use it on `h1`/`h2` only. Everything else stays system-ui. No third font.
- **The Flat Stone Rule.** Surfaces are flat at rest. Shadows appear only on copper elements, as warm glow, never as structural elevation.

### Do's and don'ts (verbatim from `DESIGN.md` § 6)

**Do:** use copper exclusively for primary actions; use the display font for h1/h2 only; use `aria-current="page"` for active nav links, not `class="active"`; constrain body text to `max-width: 65ch`; include `@media (prefers-reduced-motion: reduce)` for every animation; use `100dvh` with `100vh` fallback; use `--ease-out-expo` for entrances and `--ease-out-quart` for state transitions.

**Don't:** use Tailwind Slate colours (`#0f172a`, `#1e293b`, `#2563eb`) — the explicit anti-reference; use blue for any accent or link colour; add uppercase tracked text (the AI eyebrow pattern); use hero-metric stat cards (big number + small label); add side-stripe borders, gradient text, or glassmorphism — absolute bans; use bounce or elastic easing; animate page sections on scroll reveal; use neon green, pixel fonts, or "JOIN NOW" energy; use pastel palettes or rounded-everything.

## The footer version string

Every surface's footer shows `<PackName> · <slug>-<MC_VERSION>-v<sha>`. Three different mechanisms compute it, because two of the three containers have no git checkout:

- **pack.DOMAIN**: `build-modpack.sh` runs `git rev-parse --short HEAD` directly (it runs on the server, which has the git checkout) and bakes the string into `modpack/dist/index.html`.
- **mods.DOMAIN**: `check-updates.sh` runs inside the `mod-checker` container. It reads the _served_ pack build instead — `modpack/dist/packwiz/pack.toml`'s `version = "<sha>"` line — falling back to `git rev-parse` only if that file is missing, and to the literal string `unknown` if both fail.
- **status.DOMAIN**: `kuma-provision.py`'s `derive_pack_name()` runs inside `kuma-init`, which also has no git checkout. It fetches `http://pack-web/packwiz/pack.toml` over the internal Docker network (3 retries), parses `version`/`minecraft` out of the TOML with a regex, and falls back to `git rev-parse` (which will fail in that container) then the literal string `unknown` — so the footer can render `v<slug>-<mc>-vunknown`.

**If the status footer shows `vunknown`, that means pack-web was unreachable when kuma-init ran AND no git checkout existed — it is the diagnostic, not a bug in the footer code.** Check `pack-web` is up and reachable from `kuma-init` before touching `kuma-provision.py`.

## Fonts

The placeholder uses system fonts throughout — zero dependencies. To add a custom display font:

1. Place the `.woff2` in `modpack/template/fonts/` (this directory doesn't exist by default — create it). `build-modpack.sh` copies its contents to `modpack/dist/fonts/`.
2. Update the CSS `font-family` in **every** surface listed under "DESIGN.md is the source of truth" above.
3. Add a CORS header on `/fonts/` in `config/nginx/pack-web.conf.template` if Kuma's `customCSS` loads the font cross-origin from `pack.DOMAIN` (the location block already exists for this: `location /fonts/ { ... add_header Access-Control-Allow-Origin "*" ... }` — check it's still there, don't duplicate it).
4. CSP is `font-src 'self' data:` on every surface except status.DOMAIN, which additionally allows `https://pack.${DOMAIN}` specifically for this cross-origin font case. No other external font origins are permitted anywhere.

## Traps

1. **Editing one surface's CSS changes exactly one surface.** No shared stylesheet exists. Symptom: you fixed the nav link colour on `pack.DOMAIN` and it's still wrong on `mods.DOMAIN` → cause: you edited `modpack/template/index.html`, not `config/nginx/nav-proxy.conf.template`'s injected `.site-nav` CSS (which is what actually renders the nav on every surface, not the per-page copy).
2. **Kuma's HTML cannot be edited, only restyled.** Symptom: a UI edit to Kuma's custom CSS field survives until the next deploy, then reverts → cause: `kuma-config.json` is authoritative and `kuma-init` re-applies it on every deploy, unconditionally overwriting UI changes (`ensure_status_page()` runs every run, not just on fresh installs).
3. **`/mods/` in `pack-web.conf.template` must return a clean 404**, not the site-wide 301-to-homepage, or launchers download an HTML page instead of falling back to the Modrinth CDN. The location-level `error_page 404 = @mod_not_found` override exists specifically to bypass the site-wide redirect — don't remove it while touching nearby rules.
4. **`.toml` files must never become edge-cached.** The packwiz index (`/packwiz/`) is the auto-update signal for one-click instances; `.toml` isn't in Cloudflare's default cached-extension list — keep it that way, don't add a `Cache-Control: max-age` header to that location.
5. **`modpack/dist/` is build output.** Never hand-edit `dist/index.html`, `dist/mods/`, `dist/404.html`, or `dist/packwiz/` — the next `build-modpack.sh` run overwrites them, and some subpaths get pruned against a manifest.
6. **Deploy tiers differ per surface** (see the surface table). A pack-page change is pull tier — CI rebuilds the pack on the next deploy; a nav or Kuma styling change is infra tier and needs its container force-recreated. Predicting the wrong tier means waiting indefinitely for a change that was never going to deploy on its own.
7. **`nav-proxy-local.conf` is not a real config surface** — see "Nav injection" above. Don't spend time keeping a sixth copy in step; it doesn't exist in the pipeline.

## Validation (do not skip this)

```bash
# Nav copy count — must be 4, not 5 or 6
grep -c '<nav' config/nginx/nav-proxy.conf.template

# Verify the RENDERED config inside the container, never just the file you edited
# (nginx envsubst renders templates/default.conf.template -> conf.d/default.conf on start)
docker exec nav-proxy grep -c '<nav' /etc/nginx/conf.d/default.conf
docker exec nav-proxy grep -A2 'server_name map' /etc/nginx/conf.d/default.conf   # confirm it serves the bind mount, no "sleeping" text

# Force-recreate to pick up an nginx template change (bind-mounted, not baked into the image)
./ops restart nav-proxy
./ops restart pack-web

# Footer version string per surface
curl -s https://pack.${DOMAIN} | grep -o '·[^<]*<'
curl -s https://mods.${DOMAIN} | grep -o '·[^<]*<'
# status.DOMAIN: check the rendered footer in the browser or via curl + grep on footerText's output

# mods.DOMAIN / pack.DOMAIN reachability
curl -sI https://mods.${DOMAIN} | head -5
```

Loud failures: a missing `sub_filter` target (nginx just doesn't inject anything, page loads unstyled-nav but otherwise fine — easy to miss). Silent failures: editing `modpack/template/index.html` and expecting the nav or Kuma page to change (they don't — no shared stylesheet); editing the file you changed instead of checking the _rendered_ container config (nginx templates are bind-mounted, not baked in — a stale container keeps serving the old render until force-recreated).
