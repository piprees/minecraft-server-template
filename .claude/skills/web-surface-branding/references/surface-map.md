# Surface map — per-surface detail

Five nginx `server` blocks handle the public subdomains, split across two containers, both rendered from the same envsubst-templated nginx image (`nginx:1.30.3-alpine`):

- **`nav-proxy`** stages `config/nginx/nav-proxy.conf.template` → `/etc/nginx/templates/default.conf.template`, and holds the `map`, `status`, `pack`, and `mods` server blocks (four blocks, one file).
- **`pack-web`** stages `config/nginx/pack-web.conf.template` → `/etc/nginx/templates/default.conf.template`, and holds the root-domain redirect (`DOMAIN` → `status.DOMAIN`) plus the actual static file server that `nav-proxy` proxies `pack.DOMAIN` and `mods.DOMAIN` traffic to.

Both templates render identically for the `local` and `cloud` Compose profiles (`docker-compose.yml` services `nav-proxy`/`pack-web` — same `command:`, same `DOMAIN`/`BRAND_NAME` env vars, just a different `DOMAIN` value). **There is no separate local nav config in the current build.**

## pack.DOMAIN

- **Markup + styles:** `modpack/template/index.html` (full page, CSS custom properties in a `:root` block).
- **Regenerated by:** `scripts/build-modpack.sh`, Python `str.replace` templating (not sed) → `modpack/dist/index.html`. Runs on the server after every full deploy and is idempotent (CI re-runs it whenever mod content or the template changes).
- **Deploy tier:** Pull — the page is CI-rebuilt server-side; a consumer push alone doesn't change `dist/`.
- **How to verify it changed:** `curl -s https://pack.${DOMAIN} | grep -o '<title>[^<]*'` after the next build run, or check `modpack/dist/index.html` mtime on the server.

## mods.DOMAIN

- **Markup + styles:** HTML/CSS heredocs inside `scripts/check-updates.sh`, gated by the `--html` flag (search for `HTMLHEAD`/`HTMLBODY`/`HTMLTABLEEND`/`HTMLFOOT` heredoc markers). Colours are hard-coded hex, not CSS custom properties — there's no `:root` block to edit, you edit the literal `#0c1319` etc. inline.
- **Regenerated by:** the `mod-checker` container, on boot and daily at 06:00 UTC → writes `modpack/dist/status.html` (shares the `modpack/dist/` volume with pack-web; nav-proxy's `mods.DOMAIN` server block rewrites `/` to `/status.html`).
- **Deploy tier:** Infra — a change to `check-updates.sh` needs `mod-checker` force-recreated to pick it up; it does not touch `mc`.
- **Consumer CSS override hook:** if `/config-vol/mods-page.css` exists (seeded from `overlay/config/mods-page.css`), its contents are appended as an extra `<style>` block after the built-in one — additive, not authoritative.
- **How to verify it changed:** `./ops restart mod-checker` then `curl -sI https://mods.${DOMAIN}` or check `modpack/dist/status.html` mtime.

## status.DOMAIN

- **Markup:** Uptime Kuma's own webapp — cannot be edited, only restyled (see Trap 3 in `SKILL.md`).
- **Styles:** the `statusPage.customCSS` string in `config/uptime-kuma/kuma-config.json` (one long `!important`-heavy CSS string, hard-coded hex, no custom properties). `statusPage.footerText` sets the footer content.
- **Regenerated by:** `scripts/kuma-provision.py`'s `ensure_status_page()`, called by the `kuma-init` container on **every** deploy (not fresh-install-only — unlike `apply_settings()`, which only runs on a fresh Kuma install). It calls `api.save_status_page(customCSS=..., footerText=...)` unconditionally whenever `sp.get("customCSS")`/`sp.get("footerText")` are set in the config.
- **Deploy tier:** Infra — force-recreates `kuma-init`, which re-runs provisioning against the already-running Kuma instance.
- **Dead file — do not use:** `config/uptime-kuma/custom.css` exists on disk but is never read by any script or the compose file (verified: no reference in `scripts/`, `docker/`, or `docker-compose.yml`). `docs/customisation.md` still points at it as "Status page styling" — that line is stale. The actual mechanism is the `customCSS` string embedded directly in `kuma-config.json`.
- **How to verify it changed:** `./ops restart kuma-init` (or wait for the next deploy), then check the rendered page — Kuma's admin UI edits to custom CSS are reverted by the next `kuma-init` run regardless, so the JSON file is the only place a change persists.

## map.DOMAIN

- **What actually serves it:** a **static uNmINeD render**, served directly by `nav-proxy`'s `map` server block straight from the `./data/unmined-web` bind mount (`root /unmined-web;` — no upstream, no proxy_pass). The comment in `nav-proxy.conf.template` is explicit: "the map is always up, even while mc restarts." The `unmined-render` sidecar re-renders on a schedule (`UNMINED_INTERVAL`) and the web shell (`index.html` inside `data/unmined-web`) handles clean per-dimension URLs.
- **There is no fallback page.** `map.DOMAIN` has one behaviour: serve the static render. There is nothing to restyle for an "offline" state because there isn't one.
- **Deploy tier:** Infra — a nav/CSS change here force-recreates `nav-proxy`; the map's own tile content is unrelated to deploys entirely (the sidecar re-renders on its own schedule).
- **How to verify it changed:** `docker exec nav-proxy cat /etc/nginx/conf.d/default.conf | grep -A3 'server_name map'`.

## 404 page

- **Markup + styles:** heredoc (`NOTFOUND` marker) inside `scripts/build-modpack.sh`, hard-coded hex, no CSS custom properties.
- **Regenerated by:** `build-modpack.sh` → `modpack/dist/404.html`, served by `pack-web.conf.template`'s `error_page 404 /404.html;`.
- **Deploy tier:** Pull.

## Nav injection — the real count

`config/nginx/nav-proxy.conf.template` has **four** `server` blocks, each with its own `sub_filter '</body>' '<nav class="site-nav">...'` injection (verify with `grep -c '<nav' config/nginx/nav-proxy.conf.template` — it returns 4, not 5): `map`, `status` (Kuma), `pack`, `mods`. Each copy's `aria-current="page"` marker is hard-coded to that block's own link, which is why they can't be templated into one shared include without an extra build step.

There is **no fifth copy**. There is no map-sleeping fallback page (see above) and no separate `nav-proxy-local.conf` file feeding a sixth copy into the local Compose profile — `config/nginx/nav-proxy-local.conf` is listed in `.gitignore` (both the platform repo's and `examples/consumer/`'s), is not tracked in git, is not referenced by `docker-compose.yml` or any script, and on a checkout that has run `./dev up` at some point it may exist on disk as a **stray empty directory** (a classic Docker bind-mount artifact: mounting a host path that doesn't exist yet makes Docker create a directory there). Both `local` and `cloud` Compose profiles render the exact same `nav-proxy.conf.template` with different `DOMAIN`/`BRAND_NAME` env values. Treat any reference to a "local nav variant" or "sixth copy" as describing a mechanism that does not exist in this codebase today.

## Root-domain and OG/meta injection

The bare `DOMAIN` (no subdomain) is handled by `pack-web.conf.template`'s first `server` block: a 301 to `https://status.${DOMAIN}`. OG/meta tags are injected the same way as the nav, via `sub_filter '<title>' '<meta property="og:...">...<title>'` in each `nav-proxy.conf.template` server block — they are not present in any surface's actual page source, only in the rendered nginx output.
